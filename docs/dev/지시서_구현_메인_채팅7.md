### 4-B. F8 — 슬라이더 재계산 (계산 통로 = 우리 / 화면 = 박성인 요청서)
**정해진 것(10-30 사용자 — 진행기록 1절 "F8 결정(일부)"·"#33 병합·F8 범위 확정")**
| 항목 | 결정 |
|---|---|
| 여는 값 | 반감기 7~30일(기본 14) · 완화 세기 c 0~0.3(0.1) · 완화 상한 κ 0~80%(50%) · 묶음 비중 ω 묶음마다 0.5~2배(1배). 기본점수 B는 안 엶 |
| ω 화면 | "가중 +/−"가 아니라 뜻이 보이게 — "무엇을 더 무겁게 볼까" + 묶음별 뜻 + 합 100% 비중 막대(요청서 2절) |
| 단계 구간 | 슬라이더 값마다 다시 뽑기(ADR-018 규칙). `core.daily_table`이 이미 다시 뽑음 `[확인: half_life 21·c 0.2·κ 0.3 → 111/251/302/342]` |
| 표시 | 기본값과 다를 때만 "공식 결과 아님". 기본값이면 커밋된 결과와 같아야 함(테스트로 고정) |

**설계에서 아직 정할 것(사용자에게 템플릿으로)**
1. **ω 구현:** `core.daily_table`에 ω 키가 없음 `[확인: PARAM_KEYS 20개, T⁺ = 상승 묶음 열 순서대로 합 ÷ 개수]`. 새 params 키(예: `bundle_weights`) → T⁺ = Σ ω_g·T_g, ω_g = 배수_g ÷ Σ배수. **기본(모두 1배)에서 지금 결과와 바이트까지 같아야 함** — 가중 합은 부동소수 순서가 달라 값이 미세하게 다를 수 있음 `[해석]` → 권장: 모두 같은 배수면 지금 경로(합 ÷ 개수) 그대로 타게 하고, 시험본에서 결과 CSV 바이트 동일 확인.
2. **확장 시나리오:** 확장은 상승 묶음 4개(+제재·압박). ω 슬라이더는 기본 3묶음만? 확장도 열까? (권장: 기본만 — 요청서도 기본 3묶음)
3. **함수 이름·반환:** 요청서 4절 예정안 `load_tension_recompute(half_life=14, relief_c=0.1, relief_cap=0.5, weights=None, scenario="기본")` → (일별 표 = `load_tension_daily()`와 같은 열, 요약 dict: 단계 구간·1~5거 %·위기 10건 단계·공식과 단계 같은 날 %·`공식과_같음`) + `screen.recompute(...)`. 그림 함수(`load_tension_recompute_figure`)를 우리가 줄지, 화면이 그릴지.
4. **문서:** ADR-019(D1 "앱은 결과 CSV만 읽음"을 바꿈 — 공식 결과는 여전히 CSV, 슬라이더 결과만 앱에서 계산) · README 6절 1번 문장(F7에서 "앱 안 계산은 F8에서 다시 정한다"고 적음) · `docs/tension/산출식_변경이력.md` 새 C 번호 · `산출식.md`/`운영.md`에 슬라이더 범위.
5. 반올림: 슬라이더 결과도 요약과 같은 `np.round` 규칙(⑥ 4-D).

**만드는 순서(⑥ 방식 그대로)**
1. 위 1~5 결정 → 진행기록 1절.
2. 클라우드 사본에서 시험본: core(ω 키) · screen.recompute · loader 끝 블록 새 함수 · tests(기본값 = 커밋 결과 동일, ω·반감기·c·κ 바꾸면 구간 다시 뽑힘, 범위 밖 값 ValueError, 확장 처리) → pytest 전부 + `run_tension --end 2026-10-29` 결과 바이트 동일 + 회귀(`--end 2026-10-27`) 그대로.
3. 프롬프트 `docs/dev/tasks/F8_slider_recompute.md`(브랜치 예 `feature/tension-slider`) — 패치 글자 그대로, hash·md5·테스트 개수. 첫 커밋 = 1절 PC 작업트리 문서들 + 이 프롬프트 + ADR-019 등.
